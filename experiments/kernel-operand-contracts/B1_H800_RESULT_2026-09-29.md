# B1 H800 result — blockwise FP8 scale-layout contract

Status: **prediction supported in one SM90 run per case**. This is a latent
custom-op operand-contract finding, not a demonstrated wrong result from a
production vLLM caller and not an exact-current-`main` validation.

## Observed matrix

`rel_diff` is mean absolute output/reference difference divided by mean
absolute reference magnitude. The reference dequantizes the same FP8 operands
blockwise and uses an fp32 matmul; output is bf16. `correct` means `< 0.005`,
`wrong` means `> 0.05`; neither boundary was close in this run.

| Case | M, N, K | Predicted / observed | `rel_diff` |
| --- | --- | --- | ---: |
| Required-layout control | 256, 512, 1024 | correct / correct | 0.0014133 |
| Required-layout control (swapped dispatch) | 258, 512, 1024 | correct / correct | 0.0014133 |
| B1-a: row-major activation scales | 256, 512, 1024 | wrong / wrong | 1.0827420 |
| B1-a: row-major activation scales (swapped) | 258, 512, 1024 | wrong / wrong | 1.1223482 |
| B1-b: layouts coincide, M = 1 | 1, 512, 1024 | correct / correct | 0.0014126 |
| B1-b: layouts coincide, K = 128 | 256, 512, 128 | correct / correct | 0.0014223 |
| B1-c: N-major weight scales | 256, 512, 1024 | wrong / wrong | 0.8957120 |
| B1-c: N-major weight scales (swapped) | 258, 512, 1024 | wrong / wrong | 0.8965899 |

No case raised. Both required-layout controls passed, so the two branch
shapes were scoreable; the layout-equivalent controls passed as predicted.
For this source-equivalent SM90 path, passing the same logical scale values
in the wrong physical layout can silently change the result. The production
callers inspected in the inventory already supply the required layout.

## Limits and next decision

This is one seeded run per cell, on an older clean vLLM build whose relevant
C++ source matched both the inventory pin and the 2026-09-29 main snapshot.
It does not establish an occurrence in normal serving or prove behavior of
a newly built current-head binary. A targeted 2026-09-29 duplicate review
found no report or PR for this scale-layout contract. The four open operand
stride PRs ([#55537](https://github.com/vllm-project/vllm/pull/55537),
[#56248](https://github.com/vllm-project/vllm/pull/56248),
[#56480](https://github.com/vllm-project/vllm/pull/56480),
[#56659](https://github.com/vllm-project/vllm/pull/56659)) address operand
strides, not the scale layout; this is a scoped search result, not a guarantee
that no duplicate exists. Related precedent is the distinct Triton scale-stride
bug [#53338](https://github.com/vllm-project/vllm/issues/53338) and its
fix [#53345](https://github.com/vllm-project/vllm/pull/53345).

Before an upstream design proposal, decide whether the public custom op
should reject unsupported scale strides or document them as a caller
contract. Keep that discussion separate from the competing operand-stride
strategies; do not fold B1 into #55537 or #56248 without maintainer agreement.
