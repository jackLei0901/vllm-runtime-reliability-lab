## What this establishes

The PR's DP=1 IPC ping can distinguish this controlled EngineCore-loop stall from normal operation on the tested wheel. It tests **loop responsiveness**, not request progress or correctness of restart policy. The 60.004 s response is the configured application deadline, not a general detection-latency estimate.

## What remains open

Long-step and first-request latency, repeated concurrent probes and late replies, and the semantics of `EngineDeadError` for a recoverable stall. For DP>1, external-LB `DPAsyncMPClient` is per rank; internal-LB `DPLBAsyncMPClient` gathers every engine for the inherited health check. Whether one unresponsive engine should fail that frontend's `/health` is a design question, not an established defect; attribution and restart scope remain open. Neither DP mode was exercised.

This result adds an **in-step blocking cause** to the PR thread's `SIGSTOP` validations: a full KV-event queue blocks `ZmqEventPublisher.publish()` inside EngineCore's step. It fits [terafin's engine-loop-deadlock row](https://github.com/vllm-project/vllm/pull/36451#issuecomment-4700416311), not the loop-responsive no-progress mode addressed by [#45526](https://github.com/vllm-project/vllm/pull/45526). [F21HGG's opt-in progress watchdog](https://github.com/vllm-project/vllm/pull/36451#issuecomment-5450475299) is adjacent work, not a duplicate of the health IPC ping. F21HGG already noted that the PR reintroduces `VLLM_RPC_TIMEOUT`; [#44128](https://github.com/vllm-project/vllm/pull/44128) removed it as a dead setting. This port intentionally omitted it.

Raw logs, overlays and cell summaries remain private. Their hashes permit identity checks against retained files but **do not make the outcome independently replayable from this public set**. The public material supports review of the method, implementation delta, bounded observations and limitations; it is not an exact-head CI substitute.
