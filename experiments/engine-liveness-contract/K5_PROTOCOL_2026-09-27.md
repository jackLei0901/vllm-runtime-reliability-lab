# K5 preregistration: executor-dependent health during a bounded worker stall

Status: **GPU run not started**. This protocol is for one dual-GPU booking,
with one TP=1 cell and one TP=2 cell on separate fresh server processes. It
tests C3 in the [engine-liveness inventory](../../docs/ENGINE_LIVENESS_CONTRACT_INVENTORY_2026-09-27.md),
not shutdown C1/C2, collective progress, or a recovery policy. Review this
protocol and the runner before opening the GPUs; freeze the files before the
first cell.

## Source contract and hypothesis

Pinned vLLM Python revision:
`c8602c79062440074a018c1d5f875a5571eb6881`.

- `UniProcExecutor.execute_model` calls the local worker through
  `collective_rpc` with no deadline (`vllm/v1/executor/uniproc_executor.py:108-123`).
- `MultiprocExecutor.execute_model` passes
  `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS` into its RPC
  (`multiproc_executor.py:321-331`); a missing reply raises a typed timeout
  (`:391-405`).
- Both routes ultimately call `Worker.execute_model`
  (`vllm/v1/worker/gpu_worker.py:1019`). The experiment-only plugin holds
  rank 0 for 45 seconds **before** calling its original method; it requires a
  post-ready arm file and positive scheduled tokens.
- `/health` calls `AsyncLLM.check_health`, which tests its errored state
  (`async_llm.py:920-923`; `serve/instrumentator/health.py:22-33`). The
  launcher normally exits the API server after engine error; the run pins
  `VLLM_KEEP_ALIVE_ON_ENGINE_DEATH=1` so the health response remains observable
  (`entrypoints/launcher.py:168-190`). This is an experimental setting, not a
  claim about default deployment behavior.

Both cells pin `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=30` and the same 45-second
hold. The source predicts TP=1/`uni` remains `/health=200` while the request
is blocked and recovers after release. TP=2/`mp` should remain healthy before
30 seconds, then surface a worker-RPC timeout and `/health=503` while the hold
is still active. These are predictions; a different error chain or missing
marker is not silently interpreted as C3.

## Fixed apparatus

- Two 4090 GPUs on one Linux host. Use a cached Qwen3-4B-Instruct-2507
  checkpoint that fits one GPU. No network model download. Record model
  `config.json` SHA-256; the runner publishes only that digest.
- Installed vLLM executable whose version contains `gc8602c79`. The runner
  also requires seven decisive installed Python files to match SHA-256 values
  extracted from the pinned Git commit. A version-only match is insufficient.
  The Python package and CLI must be from the same environment.
- Both arms use eager execution, one request at a time, a 512-token maximum
  model length, `gpu_memory_utilization=0.65`, and custom all-reduce disabled.
  TP=1 explicitly selects `uni` and GPU 0; TP=2 selects `mp` and GPUs 0/1.
  The pinned `ParallelConfig` maps those names to the two executors.
- The plugin is loaded only via `VLLM_PLUGINS=llr_k5_worker_hold`. The runner
  creates a fresh `0700` output directory for each arm. Raw server logs and
  PID/start-tick markers remain private. It performs an unarmed completion and
  `/health=200` baseline before creating the arm file.
- One armed non-streaming completion follows. The plugin writes its entered
  marker only after rank-0 `Worker.execute_model` sees positive scheduled
  tokens. The runner independently binds its PID/start ticks to the live
  server's process tree before scoring. A missing or unbound marker is an
  apparatus failure, **not** evidence that no worker stalled.
- Sample `/health` every two seconds from entry through 49 seconds. Each HTTP
  probe has a 1.5-second client timeout. The health-status series, request
  outcome, release marker, server timeout log marker, and private-log digest
  are retained. No PID, hostname, model path, prompt, or raw log is printed in
  the public `K5_RESULT` line.

## Closed interpretation

| Cell | Positive result | Contradiction | Unscored examples |
| --- | --- | --- | --- |
| TP=1 / `uni` | At least five early and two late health samples; all health responses through the hold are 200; the release marker and completed request are observed; post-hold health is 200; no RPC-timeout log | Any `/health` failure during the hold | Baseline failure, no bound entry marker, release or completion unverified |
| TP=2 / `mp` | Early samples (2–26 s) remain 200; at least one 503 appears at 32–44 s, while the hold is active; the server log carries `RPC call to execute_model timed out.` | Early unhealthy response, or all late responses still 200 | 503 without the named timeout, transport failure in place of 503, missing window or marker |

Success in both cells establishes an executor-dependent detection difference
for **this bounded injected worker stall and this pinned configuration**. It
does not prove any cited upstream issue shares this root cause, that every
TP=1 stall is undetectable, or that `/health` should change globally. One run
per arm is a mechanism check, not a false-positive or reliability estimate.

## Booking and stop rule

Before starting: verify exactly two visible GPUs, enough free memory for the
cached model, the target wheel/source hashes, the CLI flags, the plugin entry
point, free local ports, and empty owner-only output locations. The CPU tests
must pass. Use a shell-level hard timeout of 12 minutes **per arm**, with 45
seconds after SIGTERM for the runner's bounded server cleanup. Run TP=1
then TP=2 sequentially, never concurrently. The runner owns server teardown;
after each arm inspect for leftover descendants and do not continue until
none remain. Stop after the first scored or unscored attempt per arm. Do not
change the hold point, timeout, or scoring windows mid-booking to rescue a
result. If a preflight or baseline fails, do not arm that cell. The host may be
shut down after raw artifacts are copied, hashed, and the owner authorizes it.

Example commands after substituting actual private paths and a reviewed GPU
environment (do not paste passwords or raw paths into the public result):

```bash
umask 077
timeout --signal=TERM --kill-after=45s 12m python \
  experiments/engine-liveness-contract/k5_health_stall_gate.py \
  --vllm /absolute/venv/bin/vllm --model /absolute/cached/model \
  --output-dir /absolute/private/k5-tp1 --port 18151 --mode tp1
timeout --signal=TERM --kill-after=45s 12m python \
  experiments/engine-liveness-contract/k5_health_stall_gate.py \
  --vllm /absolute/venv/bin/vllm --model /absolute/cached/model \
  --output-dir /absolute/private/k5-tp2 --port 18152 --mode tp2
```

Do not run the two commands until the script and plugin digests have been
frozen and reviewed. Preserve both `K5_RESULT` lines and raw-log hashes even
when a cell is unscored.
