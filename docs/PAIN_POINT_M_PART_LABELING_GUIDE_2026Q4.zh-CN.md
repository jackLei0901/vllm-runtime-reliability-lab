# M-part 标注指南（n=40 抽样附栏）

状态：**抽样前固定的判读规则（2026-09-28）**。须先公开本指南所处
commit，再抓取候选 ID 快照；快照记录本指南的公开 commit 和模型版本。适用于
[Q4 痛点发现协议](PAIN_POINT_DISCOVERY_2026Q4.zh-CN.md)
的“预注册的运行时模型附栏”，对应 [runtime model](model/RUNTIME_MODEL.md)
冻结时的版本与 commit。本指南只规定 M1–M6 附栏怎么标；V1/V2/V3 主标签
仍按 [fault taxonomy](FAULT_TAXONOMY_V0_2026-09-24.md) 的原规则，两者
互不推导。

## 0. 为什么需要这份指南

模型按源码中的**所有者**定义 M-part，而抽样读的是**用户报告**。同一份
报告（例如“卡住 → `RPC call to sample_tokens timed out` → `EngineDeadError`
→ 500”）凭直觉可以标成 M3、M4、M5 或 M6 中的任意几个。没有固定规则，
7 日后的同标注者复核主要测到的是当天的理解，`k/40` 也无法辩护。

**本 Lab 标注者熟悉 vLLM 源码，这是主要偏差来源。** 以下规则的核心是：
只标报告本身展示的东西，不把自己对源码的了解补进报告。

## 1. 总规则

1. **证据范围**：只用 issue 正文，以及协议允许读取的评论。不打开链接
   的 PR、其他 issue、源码或文档。判断理由若需要引用 vLLM 文件或行号，
   它就不是报告证据。
2. **按报告版本**：标报告者所用版本上**观察到的**行为，不按当前源码或
   固定 pin 修正。“后来的版本已经加了超时”不影响标签。
3. **观察到的边界，而非根因**：不依据猜测的根因、修复位置、CODEOWNER，
   也不依据报告者对源码的分析（例如“应该由某某负责回收 worker”）。
   报告者的**观察**（日志、状态码、时间线、对照）可以用；报告者的**解释**
   不作为标签依据。
4. **最早边界加独立异常**：先标报告中出现问题的最早边界。后续边界只有
   在**独立地**出错时才加标。它仅仅是前一个问题的正常后果时不加标。
   例如 worker 挂死期间若有存活且请求无进展的证据，可标 M3；按设计
   触发的超时与随后的 500 不自动增加 M5/M6。
5. **按设计运作的边界不标**：故障从某边界正常、如实地传过去，不算该
   边界的问题。
6. **标签数量**：通常 1–2 个。出现 4 个或更多时，重新检查规则 4。
7. **证据等级**：每个标签记一个证据指针（正文行号或评论 ID）和等级：
   报告内日志/输出，或报告者叙述（包括标题）。只有叙述也可以标，但必须
   注明。公开记录只写指针和摘要，不粘贴原始日志。
8. **顺序**：先定 V 主标签，再标 M 附栏；标完 M 后不回改 V。
9. **附带观察不入标签**：报告日志里偶然出现、报告者没有当作问题提出
   也没有展示其后果的行，即使标注者凭源码知识认出它可能有问题，也
   **不据此加标签**。把它记入单独的 `incidental_observation` 备注
   （例如指针和一句话描述），供私有台账使用。它不进入 `k/40`，也不
   计入复核一致性。
10. **按时间窗处理相反证据**：日志只证明其记录时刻的状态；不能把较早
    的 idle 外推到后来的故障窗口。若同一时间窗内日志与叙述冲突，优先
    采用日志并记录冲突；叙述仍可支持另一个时间窗，但注明证据等级。

## 2. 判定顺序（每个纳入报告依次走完）

1. **报告的问题是否完全位于模型叶子以下，且所有生命周期边界都按设计
   运作？** 这里的叶子指 kernel、模型代码、分配器、collective、数值或
   输出内容。按设计运作是指：错误原因清楚地出现在日志里，客户端得到
   明确错误，进程以非零状态退出。若是，标 `outside_model`，
   `model_parts` 为空。
2. **报告是否给出足够信息，定位至少一个服务端生命周期边界上的表现？**
   若否，标 `insufficient_information`。例如只有“卡住了”，没有状态、
   时间或进程信息。
3. **该边界是否属于模型明确未覆盖的运行时生命周期范围？** 包括
   多节点、Ray、DP coordinator 语义，或 M1–M6 中没有对应元素的情形。
   若是，标 `model_gap`，写一句模型无法表达的事实；可同时记录已知的
   相邻 M-part。
4. 其余标 `mapped`，按第 3 节逐项决定 M-part。

`outside_model` 与 `model_gap` 的区别：前者是**非生命周期**问题，而
生命周期部分表现正常；后者是**生命周期**问题，但模型还表达不了。

## 3. 各 M-part 的标注条件

只在报告**显示**下列情形时标注。

| M-part | 标注条件（报告显示……） | 不标的常见情形 |
| --- | --- | --- |
| **M1 拓扑** | 问题取决于进程角色或启动方式，并有**对照**或明确限定（例如“单 API server 正常，`--api-server-count 4` 出错”“只在 headless 下”）；或报告观察到进程归属错误：孤儿进程、错误的进程执行了动作、身份混淆 | 报告只是提到 TP=8、DP=2 等配置，没有对照；报告者推断“应由谁负责” |
| **M2 生命周期** | 某个转换**没有完成或进入了错误状态**：启动卡在就绪前、关闭没有完成、启动失败后进程或资源残留、pause/sleep/resume 后不恢复 | 转换本身正确完成，只是**报告**出错（那是 M6）；转换失败的原因明显是时间预算（那是 M5） |
| **M3 健康与进展事实** | 报告在相关时间窗分别给出 (a) 进程存活或健康判断，(b) 已接纳的请求／工作，(c) 该工作未前进，或健康判断与该工作的实际处理能力相反；三项均须有证据及等级。例如 `/health` 200 且请求不动；Running>0 而吞吐为 0；已接纳请求仍可完成却被判定为死亡 | 只有“卡住了”；idle 且没有待处理工作；只有终态崩溃（那是正常的终态报告） |
| **M4 信号** | 情况**发生期间**，本应出现的信号缺失、错误或误导：停滞期间无任何告警或只有周期性日志；存活进程被误判死亡；超时信息指向错误的操作或 rank，且报告指出或展示了这一错位 | 故障**结果**的原因丢失（那是 M6）；报告者没有说明、也未展示信号有问题，只是我们从源码知道它会误导 |
| **M5 时间预算** | 等待或截止时间是问题的一部分：无界等待（“永远等待”）；截止触发过早或过晚，且报告给出时长；嵌套或冲突的预算；在清理过程中被强杀 | 超时只是按设计把下层故障转成错误，而报告对时长没有异议（此时标下层问题所在的边界，或 `outside_model`） |
| **M6 故障与关闭传播** | 已经发生的**结果**（死亡、致命错误、主动关闭）在跨边界时原因或性质丢失或被误报：`exit code: None` 或死亡原因缺失；“see stack trace above”而上方没有栈；崩溃后退出码为 0；主动关闭被报告成崩溃；supervisor 或父进程未把失败传出去 | 原因清楚、状态码与退出码正确的正常失败 |

**M4 与 M6 的区分（最易混淆）**：M4 关于**进行中的状况**有没有正确
信号；M6 关于**已发生的结果**在跨进程时是否如实传递。停滞期间什么都
不报是 M4；死了但说不出为什么是 M6。一份报告可以两者都有，但须各自
有证据。

**M2 与 M5 的区分**：转换没完成，且报告把原因指向某个超时或宽限期，
标 M5；没有时间方面的证据，标 M2。两者都有独立证据时才同时标。

## 4. 示例（不在抽样框架内，不计入样本）

以下 issue 在 2026-09-28 均为 **open**，因此不可能进入 closed-only 的
抽样框架。标签只用于说明规则，不是样本数据，也不代表对这些 issue 的
公开结论。其中两例是合成示例，已注明。

| Issue | 报告显示 | 标签 | 适用规则 |
| --- | --- | --- | --- |
| [#41530](https://github.com/vllm-project/vllm/issues/41530) TP worker 挂起后 `sample_tokens` RPC 超时 | 00:07:34 日志显示 idle；00:08:22 起持续有警告；崩溃时统计为 `num_running_reqs=1`；报告者称有少量并发请求、worker 无响应、in-flight 请求最终返回 500 | `mapped`：**M3** | 早先 idle 不证明后来一直无需求。存活由持续警告支持，崩溃时已接纳工作由统计支持；该工作未前进主要依据报告者叙述，须分别记证据等级，不能说整段警告窗口都有 in-flight 请求。没有 `/health` 记录，不声称健康端点为 200。超时和 500 是后续处置，未称截止时间本身失当，不加 M5/M6；告警未被指为错误，不加 M4 |
| [#57429](https://github.com/vllm-project/vllm/issues/57429) ROCm 引擎停止进展后无错误死亡 | Running 56、吞吐 0、KV 不变；停滞期间只有每分钟一条日志；报告明确说没有 watchdog 消息；致命时“no worker writes an error” | `mapped`：**M3, M4, M6** | 三处各有独立证据：活着但不动（M3），期间没有信号（M4），死亡原因未传出（M6）。报告设置了 1800 s 截止但未把死亡与之关联，**不标 M5** |
| [#54184](https://github.com/vllm-project/vllm/issues/54184) liveness monitor 对健康 EngineCore 发 SIGTERM | 无异常却被发 SIGTERM；约 5.5 s 后仍有请求成功返回 200 | `mapped`：**M3, M4** | 进程仍在服务却被判定为死亡（M3）；监视信号误报（M4）。随后的 EngineDeadError 是后果，不另标 M6 |
| [#48745](https://github.com/vllm-project/vllm/issues/48745) 主动关闭时出现 EngineDeadError 栈 | 报告者说引擎没有崩溃、关闭正常完成，但 API server 在关闭序列中记录了致命错误栈 | `mapped`：**M6**；另记 `incidental_observation` | 转换正确完成，只是报告成崩溃，所以不标 M2。日志在 `timeout=0s` 时显示进程管理器进入 force-kill 分支，EngineCore 同一秒记录开始清理；秒级时间戳不能证明实际强杀与清理的先后或清理是否完成。报告者没有把它当作问题，按规则 9 **不标 M5**，只作备注 |
| [#57650](https://github.com/vllm-project/vllm/issues/57650) scheduler 初始化失败后 worker 不退出 | 注入初始化失败；新版本中 worker 卡住、显存不释放，旧版本正常退出 | `mapped`：**M2** | 启动失败后，转换没有完成清理。报告者关于“只能靠 GC 回收”的源码分析是修复位置推断，**不据此标 M1** |
| [#55632](https://github.com/vllm-project/vllm/issues/55632) ROCm 15 s 宽限被 9 s worker 强杀抵消 | 关闭时 worker 在清理中途被 SIGKILL，显存残留 | `mapped`：**M5** | 冲突的嵌套预算是最早出错的边界；清理未完成是其后果，不另标 M2 |
| [#17676](https://github.com/vllm-project/vllm/issues/17676) 等待引擎进程启动时永久挂起 | 反复打印“Waiting for 1 core engine proc(s) to start”；标题称“forever” | `mapped`：**M2, M5** | 就绪前卡住（M2）；无界等待（M5，证据等级为**报告者叙述**，因为日志只覆盖数十秒） |
| [#58565](https://github.com/vllm-project/vllm/issues/58565) CPU 上首个 embeddings 请求时 worker 崩溃 | EngineCore 记录“Worker … died unexpectedly (exit code: None)”；报告者指出缺少 worker 的真实退出原因 | `mapped`：**M6** | 死亡结果的原因没有跨边界传递。版本回归本身位于模型之外，但不改变 `mapped` 判定 |
| 合成例 A | “2 节点 TP 部署中一个节点宕机，另一节点 `/health` 仍 200，请求全部挂起” | `model_gap`（相邻 M3） | 多节点不在当前模型范围内；须写明“跨节点对等故障没有对应的模型元素” |
| 合成例 B | “运行几小时后卡住，重启就好，没有日志” | `insufficient_information` | “卡住”本身不构成 M3 证据，也没有状态、时间或进程信息 |

## 5. 复核与记录

- 7 日后同标注者复核前 10 个样本时，只使用本指南，不看首轮标签。M-part
  的分歧按标签集合逐项记录，不做多数合并。
- 标注中若发现本指南无法裁决的情形，**不当场修改指南**。按最接近的
  规则标注并写一条 `guide_issue` 备注，留到抽样结束后评议。中途修改
  指南会使前后样本不可比。
- 报告 M-part 的 `k/40` 时，同时给出每个 M-part 仅凭报告者叙述等级得到
  的数量。
