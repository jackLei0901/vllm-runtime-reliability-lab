## 两种记录，不能混算

1. **私有痛点台账**记录用户/维护者在哪个诊断边界上耗费精力。
   来源可以是现有 PR/issue、独立复现、CI flake、Lab 的 NO-GO，
   一条真实事件只保留一个去重键。它是候选池，不是统计分母。
   长期未解决的 open issue 可经每周审阅进入台账；它们不进入下述
   closed-only 样本，也不与样本计数混算。
2. **固定 n=40 issue 样本**只估计既定报告框架中，已命名的
   V1/V2/V3 分类能解释多少报告；遵循
   [fault taxonomy 的原协议](FAULT_TAXONOMY_V0_2026-09-24.md)。
   痛点附栏是描述性的，不从 issue 没提工具推断工具漏检。

## 私有台账最小模板

每条记录填写：`id`、首次见到的症状、固定来源 URL/commit 与观察日期、
受影响的进程/线程边界、缺失或误导的信号、证据等级
（同次运行材料／源码加复现／报告者叙述／未知）、目前已有的
诊断方法或 PR、下一项能区分两个解释的实验、去重键、隐私等级、
状态（新建／已分诊／PoC 候选／已退出 upstream／放弃）及原因。
不在公开台账粘贴原始进程路径、栈、模型名或私有日志。
`owner` 只能表示潜在审阅路由，不表示维护者认可。

每月最后一周最多评议三个候选，最多一个进入下一轮 PoC。
选择依据是可复现的用户痛苦、现有手段的可核查缺口、可控的
反例和明确的 upstream exit；不能按来源数量或 stars 排序。

## 40-issue 抽样预注册：先固定方法，再读正文

目标总体是固定检索框架中的、截至 2026-09-25 UTC 已关闭的 vLLM
runtime-reliability 报告，**不是**所有 vLLM 故障或生产事故。候选框架为
`vllm-project/vllm` 的 issue（不含 PR），创建于
`2026-01-01..2026-08-31`、关闭于 `2026-01-01..2026-09-25`，
在标题或正文匹配下列任一原样保留的查询词：`hang`、`stuck`、
`deadlock`、`crash`、`timeout`、`health`、`"exit code"`、
`"no progress"`。每个词独立查询，再按 issue number 取并集、去重。
这个关键词框架会遗漏别的表述；closed-only 还会漏掉持续未解决、
可能最难诊断的故障。任何覆盖率结论只对**该关键词且已关闭**的
报告框架成立，不能外推到 open issue。

检索使用 GitHub REST `GET /search/issues`（由 `gh api` 调用，
每页最多 100 条），不使用不暴露 `incomplete_results` 的
`gh search issues`。固定前缀为
`repo:vllm-project/vllm is:issue is:closed in:title,body`，加上述一个
查询词及 `created:`、`closed:` 日期约束。按**创建月份**拆分请求，
每个词、每个月独立分页；若一个分片接近 GitHub Search 可返回上限，
仅将该分片按创建日继续拆分，不改关键词。保存每个请求的完整字符串、
UTC 抓取时间、返回总数、分页数量、`incomplete_results`、所有候选
number 的排序清单与 SHA-256；任何分片不完整则停止，不抽样。
`in:title,body` 不检索评论；只在候选选定后为判读读取相关评论，
不得因此回填检索框架。
结果状态与正文可能在抓取后改变，后续复核以保留的 ID 清单和读取时
的正文版本为准，不把重跑查询得到的另一集合冒充原快照。逐项阅读
时保存 API 的 `updated_at`、标题和正文的 UTF-8 SHA-256；如引用
评论作依据，记录评论 ID、`updated_at` 和正文摘要。摘要证明读取
版本的身份，不等于公开重新发布其完整内容。

随机次序在看到正文前固定为：对每个去重候选 number 计算
`SHA256("dfxlab-coverage-20260926-v1:" + 十进制 number)`，按完整十六
进制摘要升序、number 升序作并列裁决。依次审读该顺序，按下方排除
规则筛选，直到得到 **40 个符合范围的报告**；保存实际审读的完整
前缀、每个排除代码与停止位置。若候选耗尽或框架明显无法得到 40 个，
本次为 `NO-SAMPLE`，须先发布修订协议，不能事后加词补样。
这一固定伪随机顺序使前 40 个合格项成为有界框架内的无放回样本；
不把排除后样本数当成生产故障频率。

合格项须报告 vLLM **运行时推理服务或进程生命周期**中的可观察故障。
排除代码按优先级依次为 `install_build`、`accuracy_only`、
`feature_request`、`performance_only_without_reliability_failure`、
`outside_runtime_scope`、`not_an_incident_report`。性能下降同时伴随
无进展、错误退出或健康信号失真时不按 performance-only 排除。
事实不足但仍明确报告运行时故障的条目保留，并标注
`insufficient_information`，不可为了凑满 V1–V3 将它排除。
重复报告在主样本中保留，另以固定的根因/修复链接组成重复簇做敏感性
分析；没有可核查链接时只标 `duplicate_unknown`，不凭标题相似合并。

首轮逐项记录 issue number、检索命中的词、纳入/排除及代码、V1/V2/V3/
`none_of_v0`/`insufficient_information`、最小证据指针、缺失或误导
信号（若能确认）、loop-level ping 的 `yes/no/unknown` 及依据、
重复簇、关闭方式与根因是否明确。第二次复核在首轮开始前固定为
40 个样本中哈希次序前 10 个，由同一标注者隔至少 7 日、看不到首轮
标签时重标；若未来有第二标注者，另报告独立复核，不能把同一人重标
称为独立复核。分歧与原始两轮标签均保留，不以讨论后的标签回写原记录。
