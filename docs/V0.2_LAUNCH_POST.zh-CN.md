# 当 `/health` 仍是绿色，但推理已经停止

我发布了
[vLLM Runtime Reliability Lab v0.2.0](https://github.com/jackLei0901/vllm-runtime-reliability-lab/releases/tag/v0.2.0)。
这是一个面向推理引擎故障的证据实验室，处理的是这样一类问题：服务进程仍然
存活，但真正的推理工作已经停止。

这次发布包含对已有报告
[vLLM #53859](https://github.com/vllm-project/vllm/issues/53859) 和候选修复
[#53883](https://github.com/vllm-project/vllm/pull/53883) 的独立 base/fix 验证：

- EngineCore 进程始终存活；
- `/health` 持续返回 2xx；
- 确定性的 KV-event 队列背压使 token progress 停止；
- 外部 stack 将阻塞位置定位到
  `ZmqEventPublisher.publish -> Queue.put`；
- 相同触发条件下，fix arm 保持了 token progress，同时丢弃了 4 个 event batches。

这个 bug 不是 Lab 首次发现。Lab 的作用是把已有症状和候选修复转化为一条有界、
可复现的证据链，并同时保留“活性恢复”和“事件丢失代价”两部分结论。

无需 GPU、vLLM 或 PyTorch，即可重放公开证据：

```bash
git clone --branch v0.2.0 https://github.com/jackLei0901/vllm-runtime-reliability-lab.git
cd vllm-runtime-reliability-lab
python -m pip install .
vllm-dfx replay results/vllm-zmq-backpressure-stage1-r3-20260916
```

replay 会校验关闭的文件集合、SHA-256 identity、四 cell base/fix 契约、health 与
progress 观测、阻塞 stack 结论以及已测量的 trade-off。它验证的是归档证据，不会
重新运行 GPU 实验，也不代表生产可用性。

最有价值的反馈是：实际命令、运行平台、结果，以及任何不清楚或失败的步骤。
可以使用
[结构化 replay report 模板](https://github.com/jackLei0901/vllm-runtime-reliability-lab/issues/new?template=replay-report.yml)
提交反馈。这是在邀请外部检验一份可证伪的 artifact，不是在请求 stars。
