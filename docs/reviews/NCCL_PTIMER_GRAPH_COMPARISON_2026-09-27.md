The serving classes are grouped by communicator, channel, function and event kind, so they do not arise from pooling unrelated communicators or channels. The first serving block has many distinct clocks; later blocks have only one or two distinct `AllReduce` channel-zero START values per block on each rank. That is compatible with stale-slot reuse, but the snapshots do not bind each callback to a CUDA graph node or expose `sub->base`. The AllGather clock-class contrast is an observation, not by itself a proof that AllGather is the cause.

## Source correction and falsifiable explanation

The earlier [counter-lifecycle source review](NCCL_GRAPH_PROFILER_COUNTER_LIFECYCLE_SOURCE_REVIEW_2026-09-27.md) incorrectly treated [`groupCleanup`'s planner reset](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/group.cc#L406-L424) as normal successful group completion. The source calls it on [failure paths](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/group.cc#L716-L729). On success, the planner is [reset when that communicator joins its next collective group](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/include/group.h#L125-L131). [Task preparation sets `comm->planner.persistent` from capture state](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L360-L365), and [the replay-side profiler append increments the work counter only when that field is true](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/proxy.cc#L553-L564).

The resulting **hypothesis** is call-history dependent: capture then replay alone can leave the planner persistent, consistent with the clean standalone graph. An intervening eager collective on the **same communicator** can leave the planner non-persistent; a following replay may then skip the profiler counter increment even though its retained plan is persistent. In the serving window, `AllGather` follows the 73 `AllReduce` calls on that communicator. The runner performs [model execution](https://github.com/vllm-project/vllm/blob/c8602c79062440074a018c1d5f875a5571eb6881/vllm/v1/worker/gpu/model_runner.py#L1390-L1448) before [sampling and logits calculation](https://github.com/vllm-project/vllm/blob/c8602c79062440074a018c1d5f875a5571eb6881/vllm/v1/worker/gpu/model_runner.py#L1143-L1150). This explains both the standalone negative result and why the serving repeated class is concentrated in `AllReduce`, not `AllGather`.

This is **not yet a measured internal mechanism**. Neither run recorded `comm->planner.persistent`, retained `plan->persistent`, the copied `op->workCounter`, `sub->base`, the slot counter, or the effective stream at callback time. The serving callback log also does not independently label graph mode per occurrence. We therefore cannot claim that all 73 reductions in a class share one graph, that `base=0` occurred, or that stock Inspector's execution-time/bandwidth fields are wrong.

## Next test, if a GPU booking is approved

Keep the already-run capture → replay-only cell as control A. Freeze a new small matrix before booking: B inserts one eager AllReduce on the **same communicator** between capture and replay; C inserts an equivalent eager collective on a **different verified communicator**. If B reuses callback clocks and A/C do not, the call-history mechanism gains a clean standalone reproduction. A bounded preconditioning variant can then test whether slot history changes a zero clock into a repeated nonzero clock. The exact zero/nonzero outcome should **not** be pre-asserted from these archives; it depends on counter/slot history. Require numerical completion and the same rank, library, callback and privacy checks as the prior standalone gate. No NCCL-core build, upstream issue, or Lab probe is warranted before this distinction is tested.
