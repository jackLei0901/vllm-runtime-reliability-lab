# NCCL graph-profiler `pTimer` check — one dual-GPU booking

Chinese companion: [NCCL_PTIMER_DUAL_GPU_PROTOCOL_2026-09-27.zh-CN.md](NCCL_PTIMER_DUAL_GPU_PROTOCOL_2026-09-27.zh-CN.md).

## Question and claim limit

Does the Inspector profiler receive repeated device-clock values for distinct graph-replay callback occurrences, including `KernelChStop` events emitted while a peer has not replayed? This tests the [source-reachable counter-lifetime hypothesis](NCCL_GRAPH_PROFILER_COUNTER_LIFECYCLE_SOURCE_REVIEW_2026-09-27.md) with the actual v5 `pTimer` fields. It does **not** treat a callback as proof of current device progress, infer incorrect stock bandwidth merely from repeated clocks, change the frozen `unscored / target_collective_ambiguous` serving result, or authorize an upstream report. The cheaper stock-JSON gate has already run: the repeated-sequence stratum's per-record callback delays were short on both ranks, but the completed-only records could not establish graph-position coverage or device-clock correctness. This booking therefore tests the missing device-clock data, not a skipped gate.

The source calls `recordEventState(..., ncclProfilerKernelChStop, pTimer)` before `stopEvent`; Inspector stores the stop clock in `recordEventState`. Thus the existing `kernel_ch_stop` logging site can read `stopGpuClk`. The new [delta patch](../../experiments/vllm-tp-dfx/inspector-ptimer-delta-after-occurrence-v2.29.7-1.patch) appends the raw start or stop clock to the existing occurrence marker. Raw clocks remain in private NCCL debug logs. The frozen v2 runner/parser ignore this trailing token because `EVENT_LINE` accepts whitespace after `channel=`; a CPU regression test feeds augmented lines through that parser. The separate [postprocessor](../../experiments/vllm-tp-dfx/ptimer_trace.py) publishes only communicator/channel-scoped equality-class counts, pairwise nonpositive-duration counts and SHA-256 identities, never raw keys or clocks.

**Do not score `start_(i+1) < stop_i` as a stale-clock violation.** At the pinned NCCL revision, the [device profiler writes START for every `nWorks` item](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/device/common.h#L318-L335) before running the batch and writes their STOP values after it ([kernel loop](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/device/common.h#L393-L409)). Two real work items in one batch can therefore overlap in this notation. sm_89's lack of programmatic dependent launch does not remove NCCL batching. The pinned [PyNccl call](https://github.com/vllm-project/vllm/blob/c8602c79062440074a018c1d5f875a5571eb6881/vllm/distributed/device_communicators/pynccl.py#L234-L268) also permits an explicit stream or uses the current stream; communicator identity does not prove a single stream across the whole serving run. The postprocessor's adjacent-clock counts are descriptive, not a healthy-graph pass/fail criterion.

## Pre-registered cells and stops

Use fresh owner-only private directories, a single newly built plugin binary, a bounded 30-minute build/load preflight **outside** the 180-second external timeout per cell, and no live parser edits. Preserve the exact NCCL logs, control receipt, before/during/after snapshots, build manifest and file digests privately. Do not publish raw clocks, communicator identifiers, PIDs, paths, hostnames or model output.

**Post-run amendment, not part of the frozen score:** any future booking must also verify `command -v ninja` after placing the selected serving venv's `bin` on `PATH`, before the first serving cell. The first attempt in this booking failed at engine initialization because this preflight was absent; the scored control used a fresh directory after correcting `PATH`.

1. **Read-only host and load preflight.** Confirm two GPUs, CUDA toolkit headers/library, `g++`, `make`, model and disk, and exact transferred hashes. Build both patches in a fresh pinned NCCL checkout; hash the `.so`. Confirm two rank-bound NCCL logs, the occurrence marker with a `ptimer=` suffix on start and stop, and exactly one mapped NCCL library per worker. Stop before a scored cell on a build, load or identity failure.
2. **Eager instrument control.** Run [five eager PyNccl all-reduces](../../experiments/vllm-tp-dfx/ptimer_eager_control.py) under two ranks. Its PyNccl constructor also runs one warm-up all-reduce. Require correct arithmetic, `largest_paired_group_event_count >= 6` per rank, no zero clocks, no repeated or nonincreasing clock within any communicator/channel group having at least two events, and zero paired `stop <= start` cases. The [postprocessor](../../experiments/vllm-tp-dfx/ptimer_trace.py) runs in `--end-label all` mode here and groups by communicator/channel. This strict ordering is restricted to the script's separately synchronized eager calls; it is **not** carried over to the graph control. Failure means the instrument is unvalidated; do not proceed to serving.
3. **Healthy V2 graph control.** Run the existing `serving_v2_stall_gate.py --mode control` unchanged, under its existing environment contract. Require its `healthy_v2_full_replay_observed`, valid callback ancestry, complete request and one-use receipt. Then summarize `callbacks-after.json` minus `callbacks-before.json` with the new postprocessor. Record start/stop event counts, zero-clock counts, per-communicator/channel equality classes and paired `stop <= start` counts by rank. Adjacent-clock overlap and repeated values are **not** defect predicates here: NCCL may batch several work items, other device work can rewrite a reused slot, and the serving stream boundary is not proven.
4. **One bounded hold.** Only after both controls pass, run the unchanged runner once with `--mode hold` and the exact control receipt, as in the prior runbook. Require an entered hold, pending request, stable identities and post-release completion before interpreting `callbacks-during.json` minus `callbacks-before.json`. Report closed counts for rank-0/1 start and stop events and clock equality classes. Rank-1 non-replay is a host witness, not proof of the precise device state of rank 0. No second hold, threshold change or parser repair during the booking.

The postprocessor takes `--private-dir`, `--end-label after|during`, and SHA-256 digests for the exact before/end snapshot files. It rejects missing clocks, duplicate markers, non-prefix snapshots and rank ambiguity. In `--end-label all` mode it only checks the eager instrument and takes no snapshot digests. Its JSON is closed-shape; retain it with the private archive, and publish only reviewed counts/digests. `nonincreasing_adjacent_pairs` is an eager-control sanity field and a graph-mode description, **not** a graph-mode error count. `nonpositive_pair_duration` is a one-sided anomaly count for a paired occurrence/channel, not a complete refutation test.

## Interpretation fixed before running

| Observation | Permitted conclusion | Next action |
| --- | --- | --- |
| Eager control fails the scoped, synchronized-call clock checks, or v2 control fails | Apparatus or route unscored | Stop, preserve evidence, repair offline before another booking. |
| Healthy graph control has large reused-clock classes | Device-clock reuse is observed in an otherwise completed serving run; not yet a wrong-metric claim | Compare exact occurrence/channel clocks with stock Inspector metrics and an independent timing oracle before alleging user-visible error. |
| During a valid peer hold, many distinct rank-0 occurrences share the same start/stop clock while rank 1 has not replayed | Supports the stale-slot explanation for premature callbacks, bounded to this version and route | A standalone two-rank graph/counter trace is still required for a narrow NCCL report. |
| Clocks vary during the hold, whether or not adjacent-clock counts vary | Does not refute the source path; a slot may be rewritten by concurrent work and batching can overlap work-item clocks | If worth pursuing, instrument the core predicate in a separately identified NCCL build. |
| No exact hold window or no snapshot-to-log match | Unscored | Do not substitute final aggregate logs or choose a favourable subset. |

Even a matching equality pattern is evidence about **callback data**, not the current collective's execution or the correctness of `coll_exec_time_us` / bandwidth. A graph control with zero ordering anomalies would **not** refute the source-reachable counter path, because the tested slot can change before a callback reads it; a graph control with cross-occurrence overlap would **not** prove that path, because NCCL batches work. This booking can support or remain inconclusive, not furnish a symmetric support/refute verdict. Do not admit a Lab probe or file upstream from this campaign alone. A user-visible wrong-metric claim needs a completed record bound to an occurrence and an independent timing comparison; the broader counter fix remains a source-level design hypothesis.
