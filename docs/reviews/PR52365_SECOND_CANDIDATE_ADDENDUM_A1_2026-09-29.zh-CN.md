# vLLM #52365 第二个外部候选：实测补充 A1

## 待检验的主张

在 PR 默认设置下，一个在基线和 PR 关闭上界时均能完成的请求，是否会明确因新的 60 秒事件等待而失败？整次请求耗时只用于筛选；决定性见证是关闭上界臂有**单次至少 65 秒且最终完成的事件等待**，默认臂则在事件等待中超时。EngineCore 健康与进程退出分别记录，不从请求结果推断。范围为单卡、单进程执行器（`uni`）、开启异步调度，且显式选择 V1 model runner。

## 装置事实（源码，已核对）

- 在两个固定点，V1 生成路径仅在 `use_async_scheduling` 为真时返回 PR 所等待的异步输出；关闭异步调度时该上界不作用于此路径。因此显式传 `--async-scheduling`，不依赖自动选择。
- CUDA 平台不改写 `uni` 执行器；world size 为 1 时默认即 `uni`。仍显式传 `--distributed-executor-backend uni`。
- 复制事件在复制流等待主计算流之后记录；进入等待时剩余的前向计算也计入 60 秒。
- 每个请求只生成 1 个 token；`--max-num-batched-tokens` 等于 `--max-model-len`、`--max-num-seqs 1`、关闭前缀缓存。这些设置允许不切块的 prefill，但本身不能证明实际步骤数。提示用不同 token id 列表构成；提示长度加 1 个输出 token 不得超过 `--max-model-len`。
- 公开模型的 revision 固定为提交 SHA。三臂均设置 `VLLM_USE_V2_MODEL_RUNNER=0`；这是显式 V1 配置，不代表默认 runner。

## 阶段与规则

1. **阶段 1（仅基线）：** 按预先固定、严格递增的提示长度序列测量整次请求耗时。首次成功且 ≥70 秒的档位只是*筛选点*，不是长请求；再测**恰好下一个预注册档位**后停止。只有下一档成功且也 ≥70 秒，才选它作长请求。短对照取成功且 ≤50 秒的最长档。额外档位增加耗时余量，但仍**不证明事件等待超过 60 秒**。如果首次 ≥70 秒已是最后一档、下一档失败或无合格短对照，记为 `no_candidate`，**不进入阶段 2，也不改换配置重试**。
2. **阶段 2（A/B）：** 三台新启动的服务：基线、PR 默认、PR 设 `VLLM_ENGINE_ITERATION_TIMEOUT_S=0`；每台先短后长。
   - `sitecustomize` 导入钩子在 V1 导入前包住**未改变的** `wait_for_gpu_event` 绑定，只把每次调用的时长、返回／超时／其他异常状态及限定的调用来源（`v1`／`v2`／`other`）写入私有 JSONL；runner 将记录归于依次执行的短、长请求。保留钩子 SHA-256 与私有轨迹摘要。记录缺失、损坏或被评分臂出现非 V1 调用来源都属于装置失败。
   - `supported`：三臂短请求均在 50 秒内成功，两个 PR 短请求均有有效且未超时的事件等待记录；基线长请求成功且整次请求 ≥70 秒；PR 关闭上界臂的长请求成功，单次返回的事件等待 ≥65 秒；PR 默认臂长请求失败，同一长请求窗口内既有事件等待超时记录，也有对应超时日志。
   - `not_reproduced`：上述对照及关闭上界臂 ≥65 秒等待均成立，但 PR 默认臂长请求成功。这**不推翻**期限机制：不同新启动服务的实际等待可能不同。
   - `unscored`：身份未核验（包括已有 `sitecustomize`）、轨迹缺失或 runner 路径不符、任何服务不健康、对照失败、关闭上界臂无实测 ≥65 秒可完成等待，或默认臂失败却缺少匹配的超时记录和日志。

## 推翻与限制

- `not_reproduced` 是诚实的阴性结果，不是对超时代码或默认开启风险的普遍推翻。
- 阶段 1 的 `no_candidate` 只说明固定的整请求筛选未找到成功且耗时超过 70 秒的请求；它不限制其他负载的单次事件等待。本轮不再寻找更极端配置。
- 结论不涉及生产发生率、多进程执行器中与 300 秒 RPC 预算的先后、异步调度关闭时的行为，或进程退出与重启策略。所用模型须原生支持所测上下文长度，不得用覆盖参数抬高上限；须记录其现实性理由。

## 身份、预算与发布
