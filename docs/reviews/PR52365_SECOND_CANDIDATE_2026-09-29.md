## Consumer and decision

## Source-map checkpoint (no runtime score)

The patch covers four `get_output()` sites: [V1 generation](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/worker/gpu_model_runner.py#L331-L338), [V1 pooling](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/worker/gpu_model_runner.py#L451-L460), [V2 generation](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/worker/gpu/async_utils.py#L169-L174), and [V2 pooling](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/worker/gpu/async_utils.py#L248-L255). In `UniProcExecutor`, `get_output()` runs through [`AsyncOutputFuture.result()`](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/executor/uniproc_executor.py#L32-L46); the raised exception reaches the [EngineCore result wait](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/engine/core.py#L642-L650). In `MultiprocExecutor`, the worker [turns a `get_output()` exception into a FAILURE reply](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/executor/multiproc_executor.py#L985-L997), which [the receiver raises as `RuntimeError`](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/executor/multiproc_executor.py#L426-L441). EngineCore's outer handler [treats an uncaught exception as fatal](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/engine/core.py#L1431-L1438). These are code paths, not a serving observation; frontend status and restart policy remain unscored.

The design distinction is now specific: #52365 proposes a **terminal, event-local** deadline; #55700's [stated purpose](https://github.com/vllm-project/vllm/pull/55700) is a **diagnostic stack dump** on a missed heartbeat, with no termination claimed in its PR description. Neither replaces the other's stated contract. The remaining decision is whether event polling is an acceptable cost, or whether another mechanism can provide a terminal bound without polling. The existing four fake-event tests establish helper behavior only; they do not decide that performance or recovery question. No hardware booking follows from this source review.

## The default-on question and its limit

An exact-tree `git grep VLLM_ENGINE_ITERATION_TIMEOUT_S 157bcb7c489689dd34cf28d9c9970a465d326a03 -- vllm` found only the declaration, environment-variable entry and env-name listing in `envs.py`; it found no runtime reader. This is the PR base, not merely the Lab's older `c8602c79` inventory. The patch adds a reader on the output path, with a [default of 60 s](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/envs.py#L802-L803). V1's copy stream [waits for the main stream before recording its event](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/worker/gpu_model_runner.py#L310-L329); [V2 does likewise](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/worker/gpu/async_utils.py#L137-L168). Event readiness can therefore include unfinished forward-pass work, not just the copy. The 60 s clock starts when `get_output()` enters the proposed wait, **not** when the step starts: a step whose remaining GPU work takes more than 60 s at that point could fail despite eventually completing. This is a source-backed possibility, not an observed legitimate workload or a demonstrated regression. The PR's four fake-event tests have no such slow-but-completing negative control. A control between 60 and 300 s would also expose the change in timeout ordering in multiprocess mode; it must not be assumed representative without a real workload and matching configuration. No one in the checked PR discussion has resolved the default-on policy; njhill's recorded objection addresses polling.

One constructive policy option is to default the timeout to `0` (opt-in), or introduce a separately named opt-in setting. The helper's [non-positive branch uses native `event.synchronize()`](https://github.com/vllm-project/vllm/blob/d996d76ec68e9f6a348b7b085ae1da61cb6095be/vllm/v1/worker/gpu/event_utils.py#L20-L26), so this would avoid both polling and the new fatal limit **by default**. It would not settle whether polling is acceptable when explicitly enabled, nor protect operators who do not opt in from the original [#52247 hang](https://github.com/vllm-project/vllm/issues/52247). Those are policy tradeoffs for the author and maintainers, not a proved fix.

There is a separate operational dependency, kept **off** the proposed upstream comment: the fatal EngineCore path does not by itself prove a supervisor restart. The Lab's [#52178 fault-recovery table](../../experiments/fault-recovery/README.md) observes top-level exit 0 after **SIGKILL** of EngineCore on its baseline, not after this PR's raised exception. Exit status and restart behavior for this exception remain untested here. Do not use another author's PR to promote #52178.

## Organic slow-step search (2026-09-29)

Admission requires a **successful, unmodified serving workload** with one measured `get_output()` event wait still pending after 60 s. TTFT, a whole prefill phase, startup, queueing, compilation, or an indefinite fault do not satisfy it. Public reports checked so far give leads, not an admitted workload:

| Report | Why it does not establish this wait |
| --- | --- |
| [#51454](https://github.com/vllm-project/vllm/issues/51454) | A 1M-token first question took about 66 s, but the report uses an 8,192-token batch cap. TTFT spans many prefill steps; it does not measure one event wait. Its B200/8-GPU configuration also cannot be replayed on the Lab's 4090. |
| [#54919](https://github.com/vllm-project/vllm/issues/54919) | Minutes of decode starvation during long prefill were later associated with repeated blocking D2H synchronizations and many steps, not a measured 60 s output-copy event wait. |
| [#40707](https://github.com/vllm-project/vllm/issues/40707) | A two-video request completed in 130.7 s after a scheduler fix. That is whole-request latency, with no per-event wait measurement. |

Search outcome: **no admissible real slow-step arm found; this public-report search is closed**. Public reports rarely include per-event timing, and continuing to hunt would be apparatus work without a consumer decision. Do not turn an injected delay into a claim about production prevalence or rent a GPU solely on these reports. Reopen measurement only if an operator already has a naturally slow, successful trace or an author/reviewer specifically requests it. A per-wait trace would need `get_output()` entry, event-ready time, one-step identity and request completion; only a measured wait above 60 s would qualify for the false-positive test.
