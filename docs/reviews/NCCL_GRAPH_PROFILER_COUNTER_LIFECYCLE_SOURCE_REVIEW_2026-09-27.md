# NCCL graph profiler counter lifecycle — source review

Chinese companion: [NCCL_GRAPH_PROFILER_COUNTER_LIFECYCLE_SOURCE_REVIEW_2026-09-27.zh-CN.md](NCCL_GRAPH_PROFILER_COUNTER_LIFECYCLE_SOURCE_REVIEW_2026-09-27.zh-CN.md).

## Question and boundary

Why did the [bounded TP=2 hold](VLLM_TP_V2_OCCURRENCE_ID_RESULT_2026-09-27.md#post-run-offline-callback-audit) receive `KernelChStart` and `KernelChStop` for 74 rank-0 current-replay occurrence IDs while rank 1 was held before replay? This is a **source-level reachability analysis**, not a new run, a confirmed NCCL bug report, or a change to the frozen `unscored / target_collective_ambiguous` result. The exact source is NVIDIA NCCL `v2.29.7-1`, commit `b91894bd5b190c874d98a017f93f5daa515b65d0`. The local checkout has edits only in Inspector files; all NCCL core files cited below match that commit.

## Two lifetimes that the code treats differently

| State | Source-backed lifetime and role |
| --- | --- |
| `plan->persistent` | Set from graph capture in [`ncclLaunchPrepare`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L1507-L1529). The graph retains the plan for replay; [group cleanup](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/group.cc#L391-L404) deliberately does not reclaim a persistent plan. |
| `comm->planner.persistent` | A field of the **current enqueue planner**, not the retained plan. It is set when tasks are prepared/launching ([prepare](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L360-L365), [launch](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L1507-L1511)) and cleared with the entire planner after the group ([cleanup](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/group.cc#L406-L424)). Graph replay does not repeat task preparation. |
| Host profiler counter | `comm->profiler.workCounter[channel]` is separate from both planner fields. [`incWorkCounter`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/proxy.cc#L549-L550) copies an incremented or unchanged value into `op->workCounter`. The [collective proxy op](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/include/proxy.h#L103-L115) requests an increment. |
| Device counter slots | [Communicator initialization](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/init.cc#L611-L617) allocates `workStarted` and `workCompleted` through [mapped, zero-initializing host allocation](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/include/alloc.h#L125-L133). A slot is selected modulo [64](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/include/device.h#L425-L430); [device code](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/device/common.h#L318-L335) writes counter/timestamp pairs on START and STOP/FINI. The slots are not per graph replay. |

## Path from capture to callback

1. For the inspected collective scheduling path, [`calcCollChunking` zeroes `proxyOp`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L2238-L2247), so its `workCounter` begins at zero. [`addProfilerProxyOpIfNeeded`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L563-L569) asks whether a profiler proxy is needed, then copies the operation into the retained plan's queue ([enqueue](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L106-L114)). In this inquiry, [`SaveProxyProfiler`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/proxy.cc#L553-L564) increments only when `comm->planner.persistent` is **false**. During graph capture it is true, so the queued operation can retain `workCounter=0`.
2. A graph-captured persistent plan installs a [`cudaLaunchHostFunc`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L1631-L1650); [CUDA graph capture records rather than executes stream work](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html). On replay its [`hostStreamPlanTask`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L1390-L1413) starts collective callbacks, uploads the retained proxy operations and starts the proxy. This occurs after the capture's collective group has completed and its current planner has been cleared. The plan can still say `persistent=true` while `comm->planner.persistent=false`.
3. On that replay upload, [`uploadProxyOps`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L1348-L1378) calls `ncclProxySaveOp(..., nullptr)`. In the actual append branch, [`SaveProxyProfiler`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/proxy.cc#L553-L564) increments **only if `comm->planner.persistent` is true**. If the planner is still cleared, it does not increment the retained operation's zero `workCounter`. [`ncclProxyOpToArgs`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/proxy.cc#L363-L392) copies that value to the proxy sub-argument.
4. [`profilerProxyProgress`](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/transport/profiler.cc#L18-L48) sets `sub->base=sub->workCounter` and accepts a START or STOP when `base <= slot[base % 64].counter`. The counters are unsigned: with `base=0`, **both comparisons hold for any slot value**, not merely the initial zero, before this replay's device kernel runs. START is emitted on one proxy iteration; the `continue` delays the equally eligible STOP to another iteration. The plugin then attaches those callbacks to the **current** host-created collective occurrence, although the predicate has not identified this occurrence's device work.

This is a concrete false-positive path through the pinned source, not merely an inference from event names. The [comment beside the replay-side increment](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/proxy.cc#L559-L563) states the intent to keep the proxy work counter in step with the kernel work counter during graph capture. In the normal post-group replay path, however, the retained `plan->persistent` is true while the current `comm->planner.persistent` is false, so that guarded increment is skipped. The source therefore gives a falsifiable prediction: **healthy graph replays as well as holds may emit early START and STOP**; the hold is not the cause. It also explains why an exact plugin-local occurrence ID does **not** prove an exact device-work identity: the ID binds the callback to the current host descriptor, while the proxy predicate reads a communicator-level counter slot. A nonzero but stale `base` can also pass the `<=` test against a prior value, including after modulo-slot reuse. A candidate correction would use the retained plan's capture identity and advance the counter on each replay upload, not merely once at capture; this is a design hypothesis, not a reviewed fix. Whether another thread can change the current planner during a host callback needs a separate synchronization audit.

## What the retained run does and does not establish

The digest-checked before/during snapshots show 74 asymmetric occurrence IDs, with 75 new rank-0 `kernel_ch_stop` channel events covering all 74 and zero corresponding rank-1 events. Rank 1 had not replayed, so the callbacks cannot certify current-replay completion of those collectives. Stock Inspector completed-`AllReduce` totals also rose by +21/+12, but those aggregate records are not bound to the 74 IDs. These observations fit the source path above.

The run did **not** record `plan->persistent`, `comm->planner.persistent`, `op->workCounter`, `sub->base`, or the tested slot values at callback time. It therefore does not prove which branch/value occurred for each of the 74 callbacks, nor establish the behavior of other NCCL versions, routes or devices. In particular, the source review identifies a reachable counter-lifetime mismatch; it is not yet an independently reproduced NVIDIA defect.

## Inspector metric consequence and existing-data check

Inspector copies the profiler interface's `pTimer` into its [channel start GPU clock](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L259-L284) and [stop GPU clock](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L454-L480). It derives execution time from their difference, [falling back to CPU timing](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector.cc#L1617-L1682) when GPU timing is invalid, then derives [bandwidth](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector.cc#L1558-L1593) and writes `coll_exec_time_us`, `coll_timing_source`, `coll_algobw_gbs` and `coll_busbw_gbs` ([writer](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector.cc#L487-L504)). If a current occurrence inherits another work item's `pTimer`, these **existing stock metrics** could be wrong. That is a consequence to test, **not** a user-visible symptom established by this run.

An exploratory offline read of the retained healthy-control Inspector JSON (inside the [result's digest-pinned private archive](VLLM_TP_V2_OCCURRENCE_ID_RESULT_2026-09-27.md#frozen-inputs-and-provenance)) found 388/390 completed records for ranks 0/1, of which 366/368 were `AllReduce`. All 778 records were labelled `kernel_gpu`; none reported zero `coll_exec_time_us`. The verbose `event_trace_ts` fields are [CPU callback times](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L52-L56), **not** the `pTimer` GPU clocks used for execution time. No individual 73-reduction decode step or plugin occurrence ID is bound in the stock JSON, and its retained records are sparse relative to the 1,184 request-window callbacks per rank. Thus the proposed **within-step** clustering test cannot be scored. The per-record delay from `coll_start_ts` to each `kernel_start_ts` is still measurable, without a step binding, and is registered below as a weaker callback-timing check. Repeated microsecond-rounded execution times, `kernel_gpu` labels, or nonzero bandwidth alone neither validate nor refute the counter hypothesis.

### Offline delay check, registered before computing deltas

The archive was opened earlier to count completed records and inspect field names; no per-record delay distribution has yet been computed. Freeze this rule before that computation. For each rank, select completed `AllReduce` records with a positive `coll_start_ts` and positive `kernel_start_ts`; compute one `kernel_start_ts - coll_start_ts` in microseconds per valid channel, retaining negative values as a separate integrity count. Report the count, median, 95th percentile, and fraction below 200 microseconds by rank. Also report `kernel_stop_ts - kernel_start_ts` as a secondary description, not a decision input. Do not print raw timestamps, communicator IDs, PIDs, filenames or hostnames.

Treat a `coll_sn` repeated across at least 10 retained `AllReduce` records on a rank as a **graph-candidate** stratum, not as proof of graph origin; describe the remaining records separately and do not call them eager unless an independent source binds their route. The small-delay pattern **supports only early callback delivery**, not wrong GPU execution time: both ranks must each have at least 30 valid graph-candidate channel records and at least 95% of their deltas below 200 microseconds. A median above 1 millisecond on either adequately populated rank contradicts that broad early-delivery pattern. Everything else, including insufficient retained records, is inconclusive. These thresholds are exploratory rather than calibrated to a measured step-duration baseline. Even a supportive result does not establish `base=0`, identify the device work behind `pTimer`, or demonstrate a wrong stock execution-time/bandwidth value; those require gate 2 or a separate counter trace.

### Offline result and a coverage defect in that rule

The calculation used the rule above without changing its thresholds. Each rank had **only one** repeated-`coll_sn` `AllReduce` group, containing 140/141 completed records from one communicator and three message-size classes, and yielding 165/167 valid channel delays. Their medians were 55/54 microseconds, nearest-rank 95th percentiles 115/99 microseconds, and fractions below 200 microseconds 100%/99.4% (rank 0/1). No delay was negative. Secondary `kernel_stop_ts - kernel_start_ts` medians were 15/12 microseconds. Outside that candidate group, 328/329 channel delays had medians 1,389.5/4,187 microseconds and fractions below 200 microseconds 29.9%/38.6%; these records are **not** independently labelled eager.

The preregistered numerical support threshold is met, but the rule omitted a necessary **position-coverage check**: under graph replay, one repeated sequence number can collide across distinct collective occurrences. The stock record does not bind that group to positions within a graph, so its short delays cannot show whether later collectives received premature `KernelChStart`. The sparse, completed-only Inspector export also selects survivors. Therefore gate 1 establishes a short-delay pattern in the repeated-sequence stratum but is **not discriminating** for the 74-callback hypothesis, and it establishes no wrong `pTimer`, execution time or bandwidth. This coverage defect was recognized after computing the distribution; it is not a retroactive change to the registered threshold. Gate 2 remains the decisive next check.

### Why a per-occurrence serial-clock invariant would be wrong

NCCL's [device profiler](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/device/common.h#L318-L335) loops over **all** `nWorks` in a work batch and writes each START timestamp before that batch's work runs; it similarly writes the STOP timestamps after the batch. The [kernel loop](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/device/common.h#L393-L409) confirms the START → work-batch execution → STOP order. Consequently, two real, correctly measured work items in one batch can satisfy `start_(i+1) < stop_i`. This is not evidence of a stale slot, even on sm_89 without programmatic dependent launch. `PyNcclCommunicator.all_reduce` also accepts an explicit stream and otherwise takes the current stream; a communicator identity alone does not prove one stream across a whole serving run. Comparisons across occurrences require an identified batch/stream boundary. Pairwise `stop_i <= start_i` is worth reporting as a separate anomaly count, but zero such anomalies cannot refute the counter-lifetime hypothesis.

### Post-run scope correction for the forced PyNccl TP route

The batching counterexample above is a **general NCCL possibility**, not an established explanation for the ordinary Qwen3 TP collectives in this campaign. At pinned vLLM `c8602c7`, [PyNccl `all_reduce` and `all_gather` call their NCCL APIs directly](https://github.com/vllm-project/vllm/blob/c8602c79062440074a018c1d5f875a5571eb6881/vllm/distributed/device_communicators/pynccl.py#L166-L213). [NCCL wraps each ungrouped API call in its own implicit group](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L2786-L2823), whose end submits that call's plan; [kernel launch uses the plan's stream](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L1558-L1567). vLLM's explicit grouped paths here are for [list-input](https://github.com/vllm-project/vllm/blob/c8602c79062440074a018c1d5f875a5571eb6881/vllm/distributed/device_communicators/cuda_communicator.py#L594-L603) or [symmetric-memory](https://github.com/vllm-project/vllm/blob/c8602c79062440074a018c1d5f875a5571eb6881/vllm/distributed/device_communicators/cuda_communicator.py#L620-L647) all-gathers, not the ordinary forced-PyNccl TP all-reduces.

The healthy-control summary's equal-clock class of 73 is therefore stronger than this review originally stated: it contains 73 distinct callback occurrence IDs within one communicator/channel, yet an ordinary ungrouped TP occurrence should be a separate kernel execution. Those 73 clocks cannot **all** be the actual start (or stop) time of their own separate executions. This is a post-hoc source-to-observation inference, not a new preregistered score, proof that `base=0` specifically caused it, or a stock-Inspector metric result. The published summary does not retain the class's function composition; a function-stratified check of the private logs and a standalone ungrouped graph reproduction remain useful. The single-stream adjacent-order predicate also remains unscored until the effective stream/order of the compared occurrences is bound, even though cross-occurrence clock equality is already anomalous for separate launches.

## Review conclusion and next test

The earlier “only Inspector's export policy is missing” conclusion is withdrawn for graph-replayed `KernelCh` events: an export of these callbacks could publish a false current-device-progress claim. Do not admit a Lab probe, change the v0.2 verdict, or file an upstream issue from this serving run alone.

Use the remaining gates in cost order:

1. **Offline stock JSON, completed:** the numerical threshold was met, but a single repeated sequence group per rank cannot establish coverage of later positions within a graph. Retain the closed distribution and this failed discrimination; do not turn it into a device-timing correctness claim.
2. **Plugin-only capability check, completed on one dual-GPU booking:** the [pinned result](NCCL_PTIMER_DUAL_GPU_RESULT_2026-09-27.md) reports distinct advancing eager clocks and a 73-occurrence equal-clock class in healthy forced-PyNccl TP serving. The general work-batch exception does not explain separately submitted ordinary TP calls. This is a post-hoc inference from the run and source, not a retroactive protocol score. The private archive has not been rehashed after download. Once available, audit repeated clocks by communicator/channel/function and count held-window clocks below prior history; do not invent those counts now.
3. **Standalone symptom reproduction before core instrumentation:** capture ungrouped all-reduces separated by bounded device work on two ranks, compare eager execution with graph replay, and retain an independent counter trace. This removes vLLM and directly tests whether a callback clock can belong to its named execution. Only if the mechanism remains material and ambiguous, use a separate NCCL-core build to record bounded closed facts for `plan.persistent`, `planner.persistent`, `op.workCounter`, `sub.base` and the compared slot value. That build has a new library identity, distinct from the digest-pinned wheel. A stock metric claim still needs a completed occurrence and independent timing oracle; an NVIDIA issue remains gated on a standalone reproduction and the 09-25 upstream decision.
