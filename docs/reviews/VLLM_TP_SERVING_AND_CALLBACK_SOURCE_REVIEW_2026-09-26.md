## 2. One conditional serving call chain

The table still maps a *possible* serving path, not a measured per-call route in the GPU run.

| Stage | Source fact at `c8602c79062440074a018c1d5f875a5571eb6881` | Boundary |
| --- | --- | --- |

For one-token decode, the candidate Llama row-parallel output is shaped by the model's hidden size; no model/config/tensor-size measurement was retained for this source map. Do not infer that a small decode tensor chose custom all-reduce or PyNccl. The required next witness is **the same call's** model/shape, selected backend and actual graph mode, with process/rank identity, on one pinned serving build. A startup backend list plus a graph-mode configuration is insufficient.

## 3. What the NCCL profiler callbacks mean

Inspector source boundary: NVIDIA NCCL `v2.29.7-1`, `inspector_plugin.cc` and `inspector.cc`. The lab-local patch logs only after `inspectorPluginStartEvent` has created a non-null handle for a `ncclProfileColl` or `ncclProfileKernelCh` descriptor ([patch](../../experiments/vllm-tp-dfx/inspector-start-trace-v2.29.7-1.patch), [callback](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L317-L346)).

| Observed marker | Positive claim it supports | What it cannot establish |
| --- | --- | --- |
| `CollStart` | Inspector received a collective task-start descriptor. NCCL creates it in `ncclProfilerStartTaskEvents` ([source](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/plugin/profiler.cc#L396-L420)), reached through a captured CUDA host-stream callback ([source](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L1293-L1315), [enqueue](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/enqueue.cc#L1517-L1535)). Rank 1 had this marker only in B during the window. | Device-channel start, useful work, matched peers or completion. It marks host-task execution before the kernel, not necessarily the `cudaGraphLaunch` API instant. |
| `KernelChStart` | Inspector received a channel-child start descriptor. The [device kernel writes](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/device/common.h#L292-L305) `workStarted` counters/timestamps before work; NCCL's [profiler proxy](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/transport/profiler.cc#L19-L40) polls them before starting the event ([delivery](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/plugin/profiler.cc#L584-L595)). Both A and B had an in-window marker on rank 0 but not rank 1: the lagging rank is localized at the kernel-channel-start boundary. | A completed channel, useful GPU progress, a finished all-reduce, or a general guarantee across other routes and versions. |
| Completed Inspector JSON | Inspector's completed-collective export is released only after all expected channel stop callbacks satisfy the completion check and set `commInfo->dump` ([source](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L407-L422)); its writer checks that flag ([source](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector.cc#L548-L555)). | Absence of an in-flight collective. A flat JSON record count during A and B is an export-policy limit, not proof that the interface received no start event. |

The key distinction is **acquisition versus retention/export**, not a new fault verdict. `KernelChStart` localized rank 1 as not yet observed starting its NCCL channel in both A and B, while unmodified Inspector JSON omitted the in-flight event. `CollStart` distinguished A from B because their captured host-task callbacks had different execution states; it does **not** contradict the identical kernel-channel-start state. NCCL [explicitly excludes some persistent graph-captured tasks from RAS sequence counts](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/src/plugin/profiler.cc#L422-L430), explaining why these profiler callbacks cannot be read as ordinary RAS progress counts. The simple healthy `cudaGraphLaunch` profiler smoke has no retained synchronized A/B trace, so its exact API timing remains unscored. A two-collective graph with bounded intervening device work would test whether the second `CollStart` appears before that work finishes.

## 4. Decision and review entry

**Decision:** no new NCCL acquisition probe and no upstream issue/PR from this source review. The Lab now has a small, real C++ interface exercise and a source-pinned explanation of the callback layers, but the operator-facing in-flight fact remains unavailable from unmodified Inspector. Before proposing a bounded in-flight export, obtain one real serving per-call route/graph witness and define privacy, occupancy and rate limits; an always-on callback dump would contradict the Lab's capture discipline. Source mapping is now pinned to the run's exact `c8602c7` revision; **actual serving route and graph placement** remain unverified.

Review questions: (1) Can a single serving call be bound to PyNccl and FULL/PIECEWISE replay at one revision without changing its behavior? (2) Does profiler `CollStart` retain the same semantics in that route, including capture versus replay? (3) Which closed attribution rule would consume an in-flight export, and can it explicitly return `unknown` when the producer is unavailable?
