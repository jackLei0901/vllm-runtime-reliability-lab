## 2. One conditional serving call chain

Source boundary: public vLLM commit `6af44e2887e3dbfb1c59807d1315af88f232df11`. The two-GPU callback run used a different, host-local vLLM checkout, `c8602c79062440074a018c1d5f875a55571eb6881`. That exact source is not available in the local checkouts after shutdown, so the two revisions have **not** been proven equivalent. The table maps what the public source permits; it is not a route witness for the GPU run.

| Stage | Source fact at `6af44e288` | Boundary |
| --- | --- | --- |
| Model call | Llama attention's `o_proj` and MLP's `down_proj` are `RowParallelLinear` and are called in their respective forwards ([attention](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/model_executor/models/llama.py#L175-L233), [MLP](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/model_executor/models/llama.py#L103-L121)). | Model and quantization/configuration must be pinned. |
| TP collective | `RowParallelLinear.forward` calls `tensor_model_parallel_all_reduce(output_parallel)` only with `reduce_results` and TP size > 1 ([linear.py](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/model_executor/layers/linear.py#L1761-L1785)). That function calls the TP group's `all_reduce` ([communication_op.py](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/distributed/communication_op.py#L12-L14)). | A compiler fusion or alternate model path can change the emitted operation; source syntax alone is not an observed collective. |
| Group to device | `GroupCoordinator.all_reduce` may use `torch.ops.vllm.all_reduce` or call `_all_reduce_out_place`; the latter delegates to `device_communicator.all_reduce` ([parallel_state.py](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/distributed/parallel_state.py#L722-L748)). | The custom-op route still resolves through the group; it does not fix the device backend. |
| Device backend | `CudaCommunicator.all_reduce` checks symmetric, quick, FlashInfer, AITER, custom and other backends **per call**, before PyNccl and the c10d fallback ([cuda_communicator.py](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/distributed/device_communicators/cuda_communicator.py#L335-L409)). The enabled-backends startup line is not a per-call route witness. | PyNccl is conditional on earlier branches not taking the call. A GPU-P2P failure can disable custom all-reduce, but this was not recorded as a serving-route proof here. |
| Graph placement | The v1 runner dispatches a `cudagraph_mode` for each batch, passes it through forward context, and calls `_model_forward` ([runner.py](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/v1/worker/gpu_model_runner.py#L4000-L4024), [forward](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/v1/worker/gpu_model_runner.py#L4440-L4475)). A full-graph-capable mode wraps `self.model` with `CUDAGraphWrapper` ([runner.py](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/v1/worker/gpu_model_runner.py#L5464-L5504)); its first eligible call captures `self.runnable` and later calls replay ([cuda_graph.py](https://github.com/vllm-project/vllm/blob/6af44e288/vllm/compilation/cuda_graph.py#L252-L362)). | The config names `FULL_AND_PIECEWISE` as the v1 default, but dispatch can choose PIECEWISE or NONE, and compilation/backend constraints can change the path. It has not been shown that one real serving call took PyNccl inside a replay. |

For one-token decode, the candidate Llama row-parallel output is shaped by the model's hidden size; no model/config/tensor-size measurement was retained for this source map. Do not infer that a small decode tensor chose custom all-reduce or PyNccl. The required next witness is **the same call's** model/shape, selected backend and actual graph mode, with process/rank identity, on one pinned serving build. A startup backend list plus a graph-mode configuration is insufficient.

## 3. What the NCCL profiler callbacks mean

Inspector source boundary: NVIDIA NCCL `v2.29.7-1`, `inspector_plugin.cc` and `inspector.cc`. The lab-local patch logs only after `inspectorPluginStartEvent` has created a non-null handle for a `ncclProfileColl` or `ncclProfileKernelCh` descriptor ([patch](../../experiments/vllm-tp-dfx/inspector-start-trace-v2.29.7-1.patch), [callback](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L317-L346)).

| Observed marker | Positive claim it supports | What it cannot establish |
| --- | --- | --- |
| `CollStart` | Inspector received a collective start descriptor. Its initializer records the collective function, sequence number, channel count and a host timestamp ([source](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L203-L232)). In this A/B cell, the rank-1 marker arrived before completion only for B. | Device-channel start, useful work, matched peers or completion. It must not be treated as a progress counter. |
| `KernelChStart` | Inspector received a channel-child start descriptor linked to that collective; it records a channel ID, timer pointer and host timestamp, then increments `nKernelChStarted` ([source](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L259-L293)). | A completed channel, forward GPU progress, or a finished all-reduce. The name alone does not establish when a device kernel ran. |
| Completed Inspector JSON | Inspector's completed-collective export is released only after all expected channel stop callbacks satisfy the completion check and set `commInfo->dump` ([source](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector_plugin.cc#L407-L422)); its writer checks that flag ([source](https://github.com/NVIDIA/nccl/blob/v2.29.7-1/plugins/profiler/inspector/inspector.cc#L548-L555)). | Absence of an in-flight collective. A flat JSON record count during A and B is an export-policy limit, not proof that the interface received no start event. |

The callback distinction is therefore **acquisition versus retention/export**, not a new fault verdict. It corrects the earlier device-identical hypothesis at the `CollStart` level, while the `KernelChStart` observation remained the same in the two windows. The simple healthy `cudaGraphLaunch` profiler smoke has no retained synchronized A/B trace, so host-launch timing remains separately unscored.

## 4. Decision and review entry

**Decision:** no new NCCL probe and no upstream issue/PR from this source review. The Lab now has a small, real C++ interface exercise, but the operator-facing fact is still unavailable from unmodified Inspector. Before proposing a bounded in-flight export, obtain one real serving per-call route/graph witness and define privacy, occupancy and rate limits; an always-on callback dump would contradict the Lab's own capture discipline. The exact `c8602c7` source bridge and real serving behavior remain `unverified`, not inferred from the public `6af44e288` map.

Review questions: (1) Can a single serving call be bound to PyNccl and FULL/PIECEWISE replay at one revision without changing its behavior? (2) Does profiler `CollStart` retain the same semantics in that route, including capture versus replay? (3) Which closed attribution rule would consume an in-flight export, and can it explicitly return `unknown` when the producer is unavailable?
