# Lab 架构提案：以运行时模型作为骨架

英文原稿：[Lab architecture proposal](LAB_ARCHITECTURE_PROPOSAL_2026-09-27.md)。

状态：**仅在 Lab 内进行的架构工作，尚未公开**。liveness 基线已单独保存在本地提交
`373f6dd`；本提案位于 `lab/runtime-model` 分支。它不依赖上游是否回复
[liveness 契约提纲](ENGINE_LIVENESS_RFC_OUTLINE_2026-09-27.zh-CN.md)，
也不修改已发布的 verdict、schema 或实验结果。

## 1. 核心决定

为 vLLM serving 进程树建立一个带版本的**运行时模型**，以它索引 Lab 现有的故障分类、
verdict、实验和问题入口。已有能力不搬家、不改名；改变的是组织依据：从 issue、案例和日期，
转向运行时系统里的进程、状态、信号、预算与传播边界。

这就是自上而下与自下而上的结合：模型提供骨架；新问题要么落入一个模型单元，
要么明确暴露 `model_gap`。后一种结果经月度评议后，才可能修改模型。
[完整迁移表](model/ARCHITECTURE_MAPPING_2026-09-27.md)逐项覆盖当前 22 个
`src/dfxlab` Python 模块、15 个实验目录和 27 份 `docs/` 顶层文件，
并列出不属于此模型的工作。

## 2. 为什么需要这层骨架

现有 Lab 已有证据采集、封闭 verdict、故障分类和可回放结果，却没有统一描述这些证据所指向的
**运行时系统**。同一进展事实分别出现在 `progress.py`、V1–V3/X1–X2 分类、
K1/K2/K5 与上游 `UNHEALTHY`、`/live`、`/health` 语汇中，彼此缺少映射。
另外，recorder 能保存事件前的有界历史，却还不能由 V1 无进展 verdict 触发冻结；
这是一项生产者/判定衔接缺口，不是一行 `if` 能安全补齐的功能。

## 3. 模型边界与六个组成部分

| 部分 | 内容与界限 |
| --- | --- |
| **M1 拓扑** | API/Rust 前端、CLI 父进程、DP supervisor、`MPClient`、EngineCore、executor、worker 等角色；启动模式属于单元自身，不是脚注。 |
| **M2 生命周期** | 有源码锚点的状态持有者和转换及其 owner；`paused`、`draining` 等候选公共名称仍放在契约提纲，不能倒写成当前统一枚举。 |
| **M3 健康与进展事实** | 进程身份稳定、loop 响应、已接纳需求、窗口内进展、生产者缺失或过期、已确认终止故障；每项记录范围、时效和生产者是否存在。 |
| **M4 信号** | 清单 S1–S11 的生产者、消费者及 RPC、sentinel、ZMQ、HTTP 等传输边界。 |
| **M5 预算** | 清单 T1–T14 及各入口路径上的嵌套关系。 |
| **M6 传播** | 按启动模式追踪故障如何到达 API 状态、日志/指标和进程退出码。 |

模型内部使用 M-ID；上游的 FT `UNHEALTHY` 或 `/live` 名称仅在单独映射层出现。
模型是**描述性的**：只记录固定源码能支持的行为和明确的“生产者不存在”；
期望中的契约继续放在 RFC 类文档里。每次修订保留版本、来源和变更日志，
绝不静默重评分旧结果。

范围限定为 serving 进程树与生命周期。kernel、collective、allocator、数值正确性
位于下层，只能以“worker 正在 `execute_model`”等不透明叶子连接；
暂停的 TP/NCCL 研究不会被包装成已获得的 M3 进展信号。

## 4. 现有工作如何进入模型

- V1 对应 M3 的“有需求却无进展”，S10 生产者仍缺失；V2/V3 对应 M6 的
  EngineCore/API 与 DP supervisor 退出传播。X1 是跨栈诊断生产者案例，X2 的正确性问题在模型之外。
- C1/C2/C8 进入 M5，C3 是 M3 与 M1 executor 类型的交叉，C4/C5 进入 M4，
  C6 进入 M6，C7 是未被读取的预算。它们各自的证据等级保持不变。
- `progress.py` 的五个 verdict 只建立**文档级映射**，代码和优先级不变。
  生命周期暂停/休眠与 loop ping 目前没有完整的 verdict 输入位置，应登记为映射缺口，
  不能因此重评分历史结果。
- 15 个实验目录的归属、状态和模型外项目见[完整迁移表](model/ARCHITECTURE_MAPPING_2026-09-27.md)。
  其中 `oom-boundary`、`preemption`、`soak` 是未执行 stub，是否标记 archived 尚待决定；
  标记不等于删除。

## 5. 最小仓库改动与兼容性

1. 增加 `docs/model/RUNTIME_MODEL.md` 及中文对应稿、变更日志，固定 M1–M6 的版本化定义。
2. 增加 `docs/INDEX.md`，按模型部分链接原有文档；**不移动或改名**已公开的结果与路径。
3. 为实验 README 增加 `model_cells`、`status`、`upstream_exit`、`last_scored`
   状态头；CPU 测试只验证 ID 是否存在，不能代替证据审阅。
4. 保持 `src/dfxlab`、`external-runtime-observation-v1`、v0.2 字段角色与 verdict
   优先级、`schema/`、`results/` 及隐私规则不变。不建新采集器、控制器、CLI 或注册服务。

上游采用什么术语，只更新映射层，不反复改 Lab 的模型结构。对应表需明确区分当前源码事实、
开放 PR 的设计以及已合并状态，不能把期望名称写成当前实现。

## 6. 问题入口与 Q4 计划

私有痛点台账增加 `model_cell` 或 `model_gap`。`model_gap` 经月度评议可导致版本化扩展、
被判定模型外，或保留开放。模型变化不自动增加故障分类。
若 n=40 抽样要加 M-part 标签，必须在 09-28—10-04 的 frame 冻结前预注册，
不能读完样本后补标签。

本次 liveness 工作在 Q4 #53859 PoC 门槛之前发生。内部将其归类为**模型建设**，
不是并行启动第二个 PoC；K1/K2/K5 原来的评分和限制不变，10 月选择下一 PoC 的规则也不变。
此归类不要求上游认可 Lab 的术语。

## 7. 阶段与退出条件

| 阶段 | 完成条件 |
| --- | --- |
| P0 | liveness 基线单独提交为本地 `373f6dd`；无关 TP/timeline 用户改动保持原样，未推送。 |
| P1 | 从清单写出有源码锚点的 M1–M6；迁移表每项都能归属或明确在模型外。 |
| P2 | 实验状态头、主题索引与 ID 校验测试完成；原链接仍可用。 |
| P3 | 抽样前决定是否增加 M-part 标签并记录决定。 |
| P4 | 首次月度评议对至少一个 `model_gap` 作出可复核的处置；模型零修改亦可接受。 |

季末可用三个问题检验这层骨架是否值得保留：新运行时问题能否在约十分钟内定位单元或缺口；
哪些单元没有实验是否一目了然；是否至少有一次上游审阅引用模型导出的系统事实。
若模型始终不参与选择工作，就退回参考资料，不制造维护负担。
